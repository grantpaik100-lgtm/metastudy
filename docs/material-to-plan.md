# 학습자료 → 학습·계획 반영: 현재 처리 방식과 수정 방향 (초안 v0.1)

> 작성 배경: ChatGPT에서 StudyMeta를 연결해 시험 계획을 요청했을 때 아래 두 응답이 나왔다.
>
> 1. "선택한 10과-test.pdf의 실제 내용이 현재 세션에서 열리지 않아 9–12단원의 개념 구조를
>    정확하게 분석할 수 없어. 파일로 다시 첨부해줘."
> 2. "새 자료 분석은 했지만 StudyMeta의 자료 병합 저장이 서버에서 거절돼서, Plan에 반영됐다고
>    말할 수는 없어. 9·11·12단원 내용은 확인되지 않아."
>
> 이 문서는 (1) 지금 우리 쪽 모델이 자료를 실제로 어떻게 다루는지 코드 기준으로 정리하고,
> (2) "자료는 프론트가 직접 받아 학습·계획에 반영한다"는 방향으로 무엇을 바꿀지 제안한다.
> 확정 문서가 아니라 결정을 위한 초안이다. 결정이 나면 `design.md`에 버전을 올려 반영한다.

---

## 1. 현재 처리 방식 (2026-10-01 기준, `main`)

### 1-1. 한눈에 보기

| 단계 | AI 채팅 (ChatGPT + MCP) | 서버 / DB (Supabase) | 프론트 (`service-prototype.html`) |
|---|---|---|---|
| 자료 받기 | 채팅 첨부 파일은 ChatGPT 안에만 있음. MCP로 넘어오지 않음 | 자료를 받는 도구·API·Storage **없음** | `<input type="file">`로 고르지만 **파일 이름만** 저장 |
| 자료 분석 | ChatGPT가 자기 세션에서 직접 읽을 때만 가능 (만료·미첨부 시 실패) | 없음 | 파일 이름을 그대로 스킬 이름으로 바꿈 (목업) |
| 시험 일정 | 대화 중 말로만 존재 | 테이블 **없음** | `localStorage`에 이름·날짜 저장. **시험범위 필드 없음** |
| 계획 | ChatGPT가 대화 안에서 즉석 작성. 저장할 곳 없음 | 테이블·도구 **없음** | (시험 × 스킬 × 배지) 카드를 4일 칸에 배치. 과목의 모든 스킬이 모든 시험에 들어감 |
| 학습 기록 | `record_learning_event`로 문제풀이 Evidence 기록 | `learning_events`에 append. State 자동 갱신 없음 (no-op updater) | 9개 시나리오로 State 방향만 갱신 (`localStorage`) |
| 서로 연결 | 서버의 learner context만 읽음 | — | 서버와 **연결 안 됨** (독립 목업) |

즉, **자료 → 스킬 → 시험범위 → 계획**으로 이어지는 데이터가 세 레이어 어디에도 실제로 저장되지 않는다.
그래서 채팅 AI가 매번 PDF를 직접 다시 읽어야 하고, 읽지 못하면 계획을 만들 수 없다.

### 1-2. MCP 서버 (`src/mcp/server.ts`)

등록된 도구는 3개뿐이다.

| 도구 | 하는 일 | 자료/계획 관련 |
|---|---|---|
| `get_my_learner_context` | OAuth 학생의 Profile · Domain State · Skill State · 최근 Evidence와 교수 정책 반환 | 없음 |
| `get_learner_context` | 위와 같음 (student_id 지정) | 없음 |
| `record_learning_event` | 문제풀이 Raw Event + Evidence를 `learning_events`에 추가 | 없음. 자료 저장 용도가 아님 |

- 도구가 파일 입력을 선언하지 않았으므로(`openai/fileParams` 없음) ChatGPT는 첨부 PDF를 서버로 보내지 않는다.
- 채팅 안 위젯(UI 리소스)도 없다.
- 원격 브랜치 전체를 확인한 결과, 자료·계획 도구가 있는 브랜치는 없다
  (`codex/studymeta-v2-*` 브랜치에도 `record_my_learning_event`, `render_my_learner_card`만 추가됨).

### 1-3. 배포 서버 실제 상태 (읽기 전용 조회 결과)

`get_my_learner_context`를 호출해 확인한 내용:

- 연결된 학생: Demo Student 1명
- 저장된 과목/스킬: `calculus` / `chain_rule` 하나뿐
- 최근 기록: 8/26~8/28 Chain Rule 문제풀이 Evidence만 있음. 터키어 과목, 10과 자료, 시험, 계획 관련 기록은 없음

### 1-4. GPT 응답 두 개가 나온 이유

1. **"PDF가 열리지 않는다"**: PDF가 ChatGPT 쪽에만 있다. 첨부가 만료됐거나 다른 대화에서 올린 파일을
   선택한 경우 GPT가 다시 읽지 못한다. 우리 서버는 이 파일을 받을 방법이 없다.
2. **"자료 병합 저장이 서버에서 거절"**: 우리 서버에는 "자료 병합 저장"이나 "Plan"이라는 기능이 없다.
   GPT가 할 수 있는 쓰기는 `record_learning_event` 하나뿐이다. 그래서 GPT는 둘 중 하나를 했을 가능성이 높다.
   - `record_learning_event`에 자료 분석 결과를 넣으려 함 → 스키마(`skill_id` 필수, `evidence` 1개 이상,
     `source` enum, `student_id` UUID)에서 거절됐을 것
   - 존재하지 않는 도구를 호출하려 함

   정확히 어떤 경우인지는 Vercel 함수 로그로 확인해야 한다. 어느 쪽이든 **받을 곳이 없어서** 생긴 일이다.
   GPT가 "Plan에 반영됐다고 말할 수 없다"고 한 것은 올바르게 행동한 것이다.
   "9·11·12단원 확인 안 됨"도 마찬가지다. 업로드한 자료가 10과뿐이라 범위의 나머지를 채울 근거가 없다.

### 1-5. 이미 있는 관련 기획 (미병합)

`claude/study-modes-wireframe-xf6o9p` 브랜치의 `docs/study-modes-wireframe.md`에 이미 같은 방향의
설계가 들어 있다.

- 계획모드는 **웹 전용**으로 설계됨: P-02 시험 일정·**시험범위** → P-03 자료(PDF) 업로드 →
  P-04 분석 → P-05 단원 > 개념 체크리스트
- 채팅은 `get_study_plan`(신규)으로 계획을 **읽기만** 한다
- 열린 질문 1번: "계획모드도 채팅 안에서 만들 수 있게 할지 (PDF를 채팅에 올리고 '계획 짜줘')"

이번 사례는 이 열린 질문에 대한 근거가 된다. 채팅에서 PDF를 다루면 첨부 만료, 파일 전달,
저장 거절 문제가 계속 생긴다.

## 2. 수정 방향 (제안)

### 2-1. 한 줄 요약

> **자료는 웹(프론트)이 직접 받고, 분석 결과(단원 > 개념 구조와 시험범위 대비 확인 여부)를 우리 DB에 저장한다.
> 채팅 AI는 PDF 원문이 아니라 저장된 구조와 계획을 읽는다.**

```text
[웹] 과목·시험(+범위) 등록
  → [웹] PDF 선택 → 프론트에서 텍스트·목차 추출 (원문은 선택적으로 Storage에 저장)
    → [서버] LLM으로 단원 > 개념 구조화
      → [웹] 학생이 추출 결과 확인·수정 (+ 범위 커버리지 표시)
        → [DB] 확정된 단원·개념 = 스킬 카탈로그, 시험범위 연결
          → [웹] 플래너 생성 / [채팅] get_study_plan으로 읽기
            → 학습 중 문제풀이 → record_learning_event → Evidence → State
```

### 2-2. 지켜야 할 원칙

1. **자료는 Evidence가 아니다.** 자료 분석은 "무엇을 배워야 하는지"(스킬 카탈로그)를 만들 뿐이고,
   State를 바꾸지 않는다. 새로 생긴 스킬은 "아직 시작 전" 상태로 둔다.
   이는 모델 3원칙 1(Raw Input ≠ State Update)과 `design.md` 15-2를 따른 것이다.
2. **기존 스킬을 덮어쓰지 않는다.** 아직 분석하지 않은 자료에서 찾은 개념만 추가한다(`design.md` 15-2 유지).
   같은 개념이 다시 나오면 새로 만들지 않고 출처(자료·페이지)만 덧붙인다. 이번 사례처럼 10과를 보강하는
   자료가 들어오는 경우다.
3. **학생이 확정한 것만 저장한다.** 추출은 틀릴 수 있다. "이 단원·개념이 맞나요?" 확인 단계를 거친 결과만
   스킬로 확정한다.
4. **범위 커버리지를 숨기지 않는다.** 시험범위(예: 9–12단원) 중 자료로 확인된 단원과 확인되지 않은 단원을
   함께 보여준다. 확인되지 않은 단원은 범위 텍스트만으로 할 일을 만들고, "자료를 올리면 더 정확해져요"
   배지를 단다. GPT가 "9·11·12단원 확인 안 됨"이라고 말한 상황을 화면이 먼저 보여주는 셈이다.
5. **집계하지 않는다.** 커버리지는 "단원별 확인됨/안 됨"으로만 보여준다. "범위 75% 준비됨" 같은
   합산 점수는 만들지 않는다(`design.md` 3-3, 12번).

### 2-3. 역할 분담

| 레이어 | 맡을 일 | 맡지 않을 일 |
|---|---|---|
| **프론트 (웹)** | 파일 선택, 미리보기, 텍스트·목차 추출, 시험범위 입력, 추출 결과 확인·수정 UI, 커버리지 표시, 플래너 | LLM 직접 호출 (API 키를 브라우저에 둘 수 없음) |
| **서버 (API)** | 추출된 텍스트를 받아 LLM으로 단원 > 개념 구조화, 스캔본 OCR(필요 시), DB 저장, RLS | State 계산 (기존처럼 updater 레이어 소관) |
| **채팅 (MCP)** | 저장된 계획·범위·개념 읽기, 학습 중 Evidence 기록 | 자료 분석·자료 저장 (웹으로 안내) |

**"프론트가 직접 본다"의 현실적인 범위**: 브라우저는 PDF 바이트를 읽을 수 있지만 텍스트 추출에는
pdf.js 같은 라이브러리가 필요하다. 개념 구조화에는 LLM이 필요하다.
따라서 추출(보기)은 프론트가, 이해(구조화)는 서버가 맡는 분담을 추천한다.

- 단일 HTML 프로토타입은 외부 의존성 금지(AGENTS.md 4장)라서 pdf.js를 넣을 수 없다.
  실제 추출은 빌드가 있는 서비스 웹앱 단계에서 붙인다.
- 원문을 서버로 보내지 않고 텍스트만 보내면 저작권·개인정보 부담도 줄어든다.
  다만 체크리스트 항목에서 "관련 자료 페이지"를 열려면 원문 보관이 필요하다(결정 필요 3번).

### 2-4. 데이터 모델 추가안 (Supabase)

현재 6개 테이블(`students`, `student_profiles`, `domain_states`, `learner_states`, `learning_events`,
`student_auth_links`)은 그대로 둔다. 아래를 추가한다. 이름은 초안이다.

| 테이블 | 핵심 컬럼 | 비고 |
|---|---|---|
| `subjects` | `student_id`, `domain`, `display_name` | `domain`은 기존 State 테이블의 `domain`과 같은 키 |
| `materials` | `subject_id`, `file_name`, `page_count`, `storage_path?`, `status`(uploaded/extracting/needs_review/confirmed/failed), `analyzed_at` | `status`로 "아직 분석 안 한 자료"를 판별 |
| `material_units` | `material_id`, `unit_label`(예: "10과"), `concept_name`, `skill_id`, `page_from`, `page_to` | 확정된 것만 `skill_id`를 가짐 → `learner_states`와 연결 |
| `exams` | `subject_id`, `name`, `date`, `scope_text`(예: "9–12단원"), `scope_units[]` | 시험마다 범위가 따로 있음 |
| `plan_items` | `exam_id`, `skill_id` 또는 `unit_label`, `day`, `done`, `origin`(auto/student/ai) | 학생의 드래그 재배치를 저장 |

- 모든 테이블에 RLS를 켜고, 기존처럼 서버 경유로만 읽고 쓴다.
- 계획 재배치와 완료 체크는 State를 바꾸지 않는다(`design.md` 7-4, 15-4 유지).

### 2-5. MCP 변경

| 순서 | 변경 | 효과 |
|---|---|---|
| 즉시 | `get_my_learner_context` 설명과 `teaching_context`에 "자료 저장·계획 저장 도구는 없다. 자료는 StudyMeta 웹에서 올리도록 안내하고, `record_learning_event`를 자료 저장에 쓰지 않는다"를 명시 | 이번 같은 "저장 거절" 시도와 혼란 방지 |
| DB 추가 후 | `get_study_plan` (읽기): 과목·시험·범위·단원 > 개념·커버리지·플랜 항목 반환 | 채팅이 PDF 없이 계획 기반으로 학습 시작 |
| 선택 | 채팅 업로드 지원(`openai/fileParams`로 PDF를 받아 2-1 파이프라인에 투입) | 열린 질문 1번에서 "채팅도 지원"으로 정해질 경우에만 |

### 2-6. 계획(플래너)에 반영하는 방식

- 플래너는 **해당 시험의 범위 안에 있는 스킬만** 대상으로 한다. 지금은 과목의 모든 스킬이 모든 시험에 들어간다.
- 범위 안이지만 자료가 없는 단원은 "범위 텍스트 기반" 항목으로 넣는다. 스킬이 확정되기 전이라
  State 배지가 없고, "자료를 올리면 더 정확해져요" 안내만 붙는다.
- 배치 우선순위(확인 필요 > 도움이 필요해요 > 복습 추천 > 아직 시작 전)와 시험일 이후 잠금은 그대로 둔다.
- 와이어프레임 P-05는 계획을 **단원 > 개념 체크리스트**로, `design.md` 화면 C는 **(시험 × 스킬 × 배지) 카드**로
  표현한다. 두 표현을 어떻게 맞출지 정해야 한다(결정 필요 5번).

## 4. 결정이 필요한 것

`design.md` 확정 사항을 바꾸거나 새로 정하는 항목이라 사용자 확인 후 진행한다.

1. **시험범위 필드 추가**: 시험마다 범위(텍스트 + 단원 선택)를 받는다. (`design.md` 4장 온보딩 입력 변경)
2. **추출 결과 확인 단계 추가**: 분석 후 학생이 단원·개념을 확인·수정하는 화면을 온보딩 3단계에 넣는다.

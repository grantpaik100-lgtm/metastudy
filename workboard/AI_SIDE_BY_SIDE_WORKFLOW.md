# 작업판과 AI를 나란히 사용하는 방법

이 문서는 작업판의 기능 설명서가 아니다. **작업판을 피그마처럼 계속 열어 두고, 옆의 AI와 대화하며 제품 화면을 만드는 작업 방식**을 설명한다. 사용자가 작업판 항목을 하나씩 작성하는 방식이 아니라, 사용자가 방향을 말하면 AI가 그것을 화면과 흐름으로 작업판에 표현하는 방식이다.

루미아에서는 다음과 같이 사용했다.

- 한쪽에는 작업판을 열어 전체 화면과 흐름을 계속 본다.
- 다른 한쪽에는 Codex나 Claude 같은 AI 작업 도구를 연다.
- 사용자가 원하는 방향과 어색한 점을 평소 말로 설명한다.
- AI가 실제 프로젝트 파일을 읽고 화면을 만들거나 고치며, 작업판의 화면과 연결도 작성한다.
- 사람은 작업판에서 결과를 직접 눌러 보고, 방향을 결정한다.
- 실험이 확정되면 실제 흐름에 편입하고, 폐기되면 실험실에서 정리한다.

작업판은 완성된 디자인 파일이 아니라 **사람과 AI가 같은 제품 구조를 보면서 대화하기 위한 시각적 작업대**다.

## 1. 권장 화면 배치

화면을 두 영역으로 나눠 둔다.

```text
┌──────────────────────────────────┬──────────────────────┐
│                                  │                      │
│          작업판 60~70%           │     AI 30~40%        │
│                                  │                      │
│  · 흐름도                         │  · 질문과 지시        │
│  · 와이어프레임                   │  · 코드 수정          │
│  · 실험 화면                      │  · 문제 진단          │
│  · 클릭 가능한 프로토타입         │  · 결정 정리          │
│                                  │                      │
└──────────────────────────────────┴──────────────────────┘
```

작업판을 넓게 두는 이유는 여러 화면과 연결을 한눈에 보기 위해서다. AI 창은 대화와 변경 내용을 읽을 정도의 너비면 충분하다.

가능하면 AI에게 **실제 제품 저장소 전체**를 열어 준다. 작업판만 전달하면 AI는 화면 형식만 볼 수 있고, 실제 제품 코드와 상태는 알 수 없다.

## 2. 프로젝트를 준비하는 방법

권장 구조는 다음과 같다.

```text
my-project/
├─ app 또는 src/                 실제 제품 코드
├─ docs/                         결정과 인수인계 문서
└─ workboard-template/           이 작업판
```

1. 실제 제품의 개발 서버를 실행한다.
2. `workboard-template`에서 `npm run dev`를 실행한다.
3. 작업판을 브라우저 한쪽에 연다.
4. 같은 프로젝트 폴더를 Codex나 Claude 같은 AI 코딩 도구에서 연다.
5. 작업판의 화면에 실제 제품의 로컬 URL을 연결한다.

이렇게 하면 작업판이 별도의 가짜 화면 모음이 아니라, **AI가 방금 수정한 실제 화면을 확인하는 입구**가 된다.

## 3. 사람, AI, 작업판의 역할

| 대상 | 맡는 역할 |
| --- | --- |
| 사람 | 문제와 원하는 경험을 말하고, 작업판을 보며 미감과 최종 방향을 선택한다. |
| AI | 사람의 말을 화면 구조로 번역하고, 작업판과 코드를 작성하고, 반복 수정한다. |
| 작업판 | 실험·화면·연결·현재 상태를 한눈에 보여 준다. |
| 실제 코드 | 최종 화면과 동작의 정본이다. |
| 문서 | 왜 그렇게 결정했는지 남긴다. |

중요한 결정은 [DECISIONS.md](./DECISIONS.md)에 기록한다. AI와 새 작업을 시작할 때 실제 코드, 작업판 상태와 함께 이 결정 장부를 먼저 읽게 한다.

사람이 화면명과 필드를 하나씩 설계해 AI에게 받아 적게 하는 것이 아니다. 사람은 “설문처럼 무겁지 않았으면 좋겠다”처럼 방향을 말할 수 있다. AI는 그것을 화면 목적, 정보 블록, 연결과 실제 코드로 바꾼다. 작업판에서 직접 본 뒤 사람이 선택한다.

## 4. 기본 작업 순환

한 번의 큰 지시로 전체 서비스를 만들기보다 아래 순환을 짧게 반복한다.

### ① 작업판에서 현재 위치를 고른다

지금 다루는 화면이나 연결을 하나 고른다. AI에게 화면 이름, 현재 URL, 앞뒤 화면을 알려 준다.

### ② AI에게 작은 결과 하나를 요청한다

“전체를 개선해 줘”보다 변경 범위를 정확히 말한다.

```text
지금 작업판에서 ‘가입 전 소개’ 화면을 보고 있어.
실제 화면은 /onboarding/intro야.
이 화면의 목적은 사용자가 10초 안에 서비스 가치를 이해하는 거야.
현재 파일을 먼저 읽고, 정보 순서만 고쳐 줘.
색상과 공통 네비게이션은 바꾸지 마.
수정 후 확인할 URL과 바뀐 이유를 알려 줘.
```

### ③ 작업판에서 실제 결과를 확인한다

AI의 설명만 보고 승인하지 않는다. 작업판의 폰 프레임이나 실제 URL에서 다음을 확인한다.

- 첫 시선이 어디로 가는가
- 다음 행동이 분명한가
- 앞 화면에서 자연스럽게 이어지는가
- 뒤 화면으로 이동할 수 있는가
- 모바일 크기에서 잘리거나 겹치지 않는가

### ④ 보면서 바로 피드백한다

추상적인 평가보다 눈에 보이는 문제를 지시한다.

```text
지금 작업판에서 보니 제목과 버튼의 힘이 비슷해.
버튼은 그대로 두고 제목 위계를 한 단계 낮춰 줘.
설명은 두 줄을 넘지 않게 해 줘.
```

### ⑤ 흐름에 편입하거나 실험을 끝낸다

결과가 괜찮으면 와이어프레임과 흐름도에 정식 화면으로 넣는다. 아직 확신이 없으면 실험실에 남긴다. 필요가 없어졌다면 보류 또는 삭제한다.

## 5. 네 공간을 AI와 사용하는 법

### 실험실: 하나의 질문을 빠르게 시험한다

실험실에는 완성 화면을 쌓지 않는다. 답을 구하려는 질문 하나와 비교 가능한 시안을 둔다.

좋은 예:

- 첫 화면에서 설명을 먼저 보여 줄지 결과 예시를 먼저 보여 줄지
- 검색을 탭으로 둘지 첫 화면에 노출할지
- 한 페이지 입력과 단계별 입력 중 어느 쪽이 이해하기 쉬운지

AI 요청 예시:

```text
이 기능을 실제 흐름에 넣기 전 실험하려고 해.
프로덕션 화면은 수정하지 말고 /lab/search-entry에 A/B 두 안을 만들어 줘.
A는 검색창 우선, B는 추천 카드 우선으로 구성해.
비교할 항목은 첫 행동의 명확성, 정보량, 모바일 높이야.
```

결론이 나면 선택한 안만 실제 화면으로 옮기고 실험의 상태를 기록한다.

### 와이어프레임: 화면 안의 정보 순서를 합의한다

여기서는 색상과 장식보다 화면의 목적, 정보 블록, 주요 행동을 본다.

AI 요청 예시:

```text
‘주문 확인’ 화면의 목적과 필요한 정보를 먼저 정리해 줘.
필수 정보, 보조 정보, 주요 버튼 순서로 제안하고
빠진 정보가 있으면 코드 수정 전에 알려 줘.
합의한 순서로 실제 화면을 구현해 줘.
```

와이어프레임은 실제 화면과 따로 노는 문서가 되기 쉽다. 구조가 확정되면 실제 URL을 연결해 같은 자리에서 확인한다.

### 흐름도: 화면보다 관계를 본다

흐름도는 피그마 캔버스처럼 사용한다. 카드를 옮기고 연결하면서 다음을 찾는다.

- 시작점이 여러 개인가
- 막다른 화면이 있는가
- 같은 화면이 중복되어 있는가
- 사용자가 되돌아갈 수 있는가
- 성공, 실패, 취소 경로가 있는가
- 실험 화면과 실제 화면이 섞여 있지 않은가

AI 요청 예시:

```text
내보낸 작업판 JSON과 현재 라우트를 비교해 줘.
막다른 화면, 코드에는 있지만 흐름도에 없는 화면,
흐름도에는 있지만 실제 라우트가 없는 화면을 나눠서 알려 줘.
아직 파일은 수정하지 마.
```

진단을 확인한 뒤 필요한 연결만 하나씩 추가한다.

### 목업·프로토타입: 설명보다 클릭으로 검증한다

목업은 모양을 확인하고, 프로토타입은 사용 순서를 확인한다. 실제 URL을 연결할 수 있다면 사본을 만들기보다 실제 화면을 보여 주는 편이 좋다.

AI 요청 예시:

```text
첫 방문 흐름을 시작 화면부터 완료 화면까지 직접 점검해 줘.
각 단계에서 다음 행동이 하나로 읽히는지 확인하고,
문제가 있는 화면과 이유만 먼저 보고해 줘.
내 승인 전에는 수정하지 마.
```

AI가 브라우저를 직접 볼 수 없는 환경이라면 현재 화면의 스크린샷, URL, 작업판 JSON 중 필요한 것을 전달한다.

## 6. AI에게 지시할 때 항상 포함할 것

아래 다섯 가지를 넣으면 시행착오가 줄어든다.

1. **현재 위치** — 작업판의 어느 방과 어느 화면인지
2. **화면 목적** — 사용자가 여기서 이해하거나 해야 하는 일
3. **변경 범위** — 이번에 바꿔도 되는 파일과 요소
4. **유지할 것** — 공통 UI, 데이터 계약, 이미 확정한 결정
5. **완료 조건** — 어떤 URL에서 무엇을 확인하면 끝인지

복사해서 시작할 수 있는 형식:

```text
현재 위치:
화면 URL:
이 화면의 목적:
이번에 해결할 문제:
바꿔도 되는 범위:
유지해야 하는 것:
완료 조건:

먼저 관련 파일을 읽고 현재 상태를 설명해 줘.
그다음 필요한 변경을 적용하고 확인 방법을 알려 줘.
```

## 7. 작업판과 AI가 어긋나지 않게 하는 규칙

### 실제 화면을 정본으로 둔다

가능하면 작업판 안에 화면 사본을 다시 만들지 않는다. 실제 제품 URL을 연결하면 AI가 코드를 고친 결과가 작업판에도 바로 나타난다.

### 실험과 확정 화면을 구분한다

아이디어가 있다는 이유만으로 실제 흐름에 넣지 않는다. 실험실에서 확인한 뒤 확정된 것만 흐름도로 옮긴다.

### 한 번에 한 문제를 다룬다

화면 구조, 카피, 색상, 데이터 연결을 한 요청에 모두 넣으면 무엇이 좋아졌는지 판단하기 어렵다. 확인 가능한 단위로 나눈다.

### AI의 보고보다 화면을 믿는다

AI가 “완료했다”고 말해도 작업판에서 직접 확인한다. 보이지 않는 상태라면 완료로 취급하지 않는다.

### 결정 이유를 남긴다

화면을 채택하거나 폐기했을 때 이유를 [DECISIONS.md](./DECISIONS.md)에 적는다. 모든 사소한 수정을 기록하지 않고 여러 화면에 영향을 주거나 되돌리기 비싼 결정만 남긴다. 다음 AI 세션과 다른 팀원이 같은 논의를 반복하지 않게 된다.

AI에게는 다음처럼 시작하도록 요청할 수 있다.

```text
작업 전에 README.md, AI_SIDE_BY_SIDE_WORKFLOW.md, DECISIONS.md를 읽어 줘.
확정 상태의 결정을 제약조건으로 취급하고,
그 결정을 바꿔야 한다고 판단하면 바로 수정하지 말고 이유와 영향부터 보고해 줘.
```

## 8. 템플릿에서 현재 내용을 AI에게 보여 주는 방법

이 템플릿의 입력 내용은 브라우저 로컬 저장소에 있다. AI가 같은 프로젝트 폴더를 열었다고 해서 브라우저의 현재 화면 목록을 자동으로 읽는 것은 아니다.

현재 상태를 AI와 공유할 때는 다음 중 하나를 사용한다.

- 상단 **AI와 함께 → AI 요청문 복사**로 현재 JSON을 대화에 붙여 넣기
- 상단 **내보내기**로 JSON을 저장해 AI에게 읽게 하기
- 현재 작업판 또는 실제 화면의 스크린샷 전달하기
- 실제 제품 화면의 로컬 URL과 관련 파일 경로 알려 주기

AI가 수정한 JSON을 받을 때는 기존 내용을 먼저 내보내 백업하고, 작업판의 **불러오기**로 반영한다. 불러온 뒤에는 반드시 흐름도와 프로토타입에서 확인한다.

## 9. 동료에게 전달할 핵심 문장

> 작업판은 AI가 대신 완성하는 문서가 아닙니다. 작업판을 한쪽에 계속 열어 두고, 옆의 AI에게 작은 변경을 맡긴 뒤, 사람이 실제 화면과 전체 흐름을 보며 계속 방향을 선택하는 방식입니다.

형식보다 이 반복 방식이 핵심이다.
